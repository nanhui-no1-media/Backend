# 认证码是一条验证通道（后台生成 / 兑换即通过）

日期：2026-09-26 · 与 jinha 协作

需求：新增**认证码**验证通道——有权限的用户在后台生成认证码，码带**有效期**与**可用次数**；创建由后台直接创造、**前端零生成代码**；归属于既有验证 / 审核体系。

**账号「已验证」仍是任一通道 approved。** 认证码落成第 4 条通道（`authcode` / 认证码）：成员兑换即写 approved（记 `identifier` = 码原文、`verified_by` = 发码人），无 pending、无人工环节。

规则：

- **生成侧只在 Django 后台**：标准 CRUD 权限（`accounts.add_authcode` 等四件套，默认授「社长」「信息组」）；生成 / 吊销不受站点「验证通道」开关约束（可先备码），兑换侧受约束。
- **有效性** = 有效期（必填）+ 可用次数（默认 1，一码可供多个账号各用一次）；过期 / 吊销 / 用尽只停**后续**兑换，**不回溯**已通过者——收回信任走「停用账号」。
- **每账号至多一次**（唯一约束兜底）；已通过任意通道者再兑换 → 拒绝且不消耗任何码。
- **兑换失败按账号节流**（只计失败、成功不占额度；额度进站点策略）。
- **零常驻**：过期惰性判定，无定时任务、无邮件通知；兑换记录 = 审计留底（码详情页内嵌 + 全局只读列表）。

## 被否方案

- **前端做生成 / 管理页**：用户明确「前端不要有生成认证码的代码」；生成是后台操作，需要管理权限 + `is_staff` 双重收口。否。
- **吊销 / 过期时回溯撤销已通过用户**：兑换是**历史事件**（与人工审批同类）；回溯会让已验证用户凭空掉级（内容可见性、写门禁连锁）。收回信任有「停用账号」这条正路。否。
- **独立于验证通道模型的新系统**：与 ADR-0006 多通道模型重复，且会引入第二条 `is_verified` 判定源。否（作为第 4 条通道扩展）。
