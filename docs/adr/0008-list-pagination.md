# 列表分页：DRF 默认分页 + 前端混合交互（主列表页码 / 辅助列表加载更多）

## 背景

列表接口（任务、新闻、活动、提案、会话、用户）在大数据量下存在性能问题：无上限接口一次性返回全量，有上限接口静默截断。审查发现**后端其实已经分页了**——`config/settings.py` 全局配置 `DEFAULT_PAGINATION_CLASS = PageNumberPagination`、`PAGE_SIZE = 20`，所有 DRF `ModelViewSet.list` 都返回 `{count, next, previous, results}` 信封。真正**无界**的只有两处：

- `/auth/users/`：一次返回全部激活用户（任务表单指派下拉框在用），无搜索无分页。
- `/messaging/conversations/messages/`：整条会话全量返回（消息页 / 任务讨论区在用），无上限。

而**前端大部分没有适配分页**：新闻页有完整页码器，但任务/活动/提案/会话侧栏都写 `data.results || data` 单次拉取，一旦超过 20 条就静默截断——用户看不到第 21 条，也感知不到还有更多。另有三个隐蔽问题：`tasks/tags` 被 DRF 默认分页，标签超过 20 个后第 21 个起选不到；`ConversationViewSet.list` 无 ordering 乱序；任务时间线/甘特图视图共享列表页同一状态，只画到当前页的前 20 条。

## 决策

1. **后端以 DRF `PageNumberPagination` 为唯一分页机制**（即"用 Django 自带的"）：沿用全局默认 `PAGE_SIZE = 20`，不引入自定义分页类，不用 `django.core.paginator.Paginator`。
2. **无界端点补齐分页**：
   - `/auth/users/` 改为 DRF 分页 + `?search=`（按用户名/昵称模糊）——供任务表单搜索式下拉框。
   - 会话消息改为**倒序分页**（`-created_at`），最新优先。
3. **前端混合交互**：
   - **主列表**（任务 / 活动 / 提案 / 会话侧栏）用**数字页码器**，与新闻页同款；筛选/搜索变更时页码重置回第 1 页。
   - **辅助列表**（消息线程、个人主页内容面板、会话历史）用**加载更多**追加。
   - **消息线程**最新优先展示，向上"加载更早的消息"往前翻，追加到顶部。
   - **任务表单指派下拉框**改搜索式：防抖输入即搜，选中回显。
4. **前端抽共享基建**：`<Pagination>` 组件 + `usePagedList` 钩子（封装 `{data, loading, page, total, setPage}`）+ `<MessageThread>` 组件（消息页 / 任务讨论区复用），避免 5 处复制页码器、2 处复制加载更早逻辑。
5. **全量逃生舱 `?all=1`**：任务时间线/甘特是"看全局"的视图，分页语义不适用——切换视图时用 `?all=1`（跳过分页、配合现有筛选/搜索）拉全量。只给真正需要的端点加，不加全局。
6. **标签一律不分页**：`tasks/tags` 关掉 DRF 分页，与 `news/tags` 对齐。标签是人工维护、数量有界的下拉数据源，分页一个下拉框是反模式。
7. **半壳信封补全**：`users_view` / `sessions_view` / `user_content_view` 目前返回 `{results}` 缺 `count/next/previous`，统一补全为 DRF 信封。

## 被否的方案

- **列表页全部用加载更多 / 无限滚动**：任务列表要翻找老任务，页码器更直接；且新闻页已有页码器先例，统一优先。
- **列表页全部用数字页码**：消息线程、个人主页小列表用页码器笨重，加载更多更贴合。
- **标签也分页 + 服务端搜索**：只有标签上千才有必要，当前量级属过度设计。
- **三种任务视图都吃当前页数据**：甘特图只画前 20 条会误导人；`?all=1` 逃生舱是 Django 处理"分页 + 全量视图"的标准做法。

## 后果

- 前端各列表页（任务/活动/提案/会话侧栏）从 `data.results || data` 静默截断改为真实分页，行为可见可预期。
- `tasks/tags` 关分页后修复"前 20 之后选不到"的隐患。
- 会话侧栏补 `-updated_at` 排序（顺带修复乱序）。
- 消息线程改为倒序分页后，前端需维护"顶部加载更早"的本地拼接状态。
- `?all=1` 是大数据量下的性能妥协点：全量视图仍会慢，但语义正确；若将来数据量进一步膨胀，需单独优化（如甘特只拉聚合）。
