# 不抽取 任务 / 申报 共享生命周期基类

任务（Task）和申报（Proposal）都带 `STATUS_CHOICES`、`reject_reason`、`reviewed_by`、以及 approve/reject 类动作，表面相似。决定**不**抽取共享基类或混入；两者保持各自独立的状态机与权限规则。

## 理由

`CONTEXT.md` 明确：申报是一个**双用途容器**（活动申报 + 意见反馈，靠 `proposal_type` 区分），其状态空间与任务不同——

- 任务：`pending → in_progress → reviewing → completed / cancelled`
- 申报：`voting → pending_approval → returned / approved / rejected / withdrawn`，且带一道**投票门**

两者只是"字段同名、动作同名"，**语义不同**。共享基类只会是一个横跨两台不同状态机的**浅抽象**：把不同的转移规则与权限规则塞进一个泛化父类，领域概念被实现细节稀释。

**删除测试**：删除一个假想的共享基类，只会把本就不同的逻辑退回各自模型——复杂度并未集中，只是搬动。不通过。

## 被否的方案

- **共享基类（如 `BaseReviewableModel`）**：能消除字段重复，但把两套不同的状态转移与权限规则压进一个泛化抽象，违反领域边界；"可审批"是一个实现巧合，不是领域概念。
- **仅抽字段混入（`reject_reason` / `reviewed_by`）**：去重收益极小（几个字段），却引入一层继承与间接，得不偿失。

## 后果

- 任务与申报的生命周期深化**各自独立**进行（任务侧见 #6）。
- 若未来两者真的出现**相同的状态转移规则**（不止是字段/动作同名），届时再重开本 ADR。
- 此记录旨在让后续架构评审**不再重复建议**此抽取。
